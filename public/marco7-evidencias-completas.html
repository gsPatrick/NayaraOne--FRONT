EST-001 — Item mestre único por empresa/SKU (não duplicar material por obra)

Resolvido

O que o Caderno exige, em linguagem simples: cada material/ferramenta/ativo tem UM cadastro só por empresa, identificado pelo SKU. Nenhuma obra pode criar "o mesmo cimento" de novo com outro registro — isso quebraria qualquer cálculo de saldo, custo médio ou relatório consolidado entre obras.

Como funciona
O catálogo é a tabela inventory.items (model InventoryItem), com unicidade reforçada em dois níveis: (1) checagem de aplicação em createItem (items.service.js) que busca por { companyId, sku } antes de criar e lança INVENTORY_ITEM_DUPLICATE_SKU se já existir; (2) sku/unitOfMeasure são obrigatórios (TAB-0750 — contrato de banco trata as colunas como NOT NULL, com UNIQUE(company_id, sku) real no schema), então mesmo um bypass do service não teria como persistir um SKU duplicado — o Postgres rejeitaria. O item é único "por empresa", não por obra: as obras (InventoryLocation.locationType = 'PROJECT_SITE') referenciam o mesmo inventoryItemId em seus movimentos/saldos (inventory.stock_balances é chaveada por (inventoryItemId, locationId), nunca duplicando o item mestre). Isso significa: "cimento CP-II" tem um único registro em InventoryItem, e cada obra só tem saldo próprio daquele mesmo item em seu local.

EST-002 — Movimento append-only (entrada, saída, devolução, transferência, ajuste, perda, descarte)

Resolvido

O que o Caderno exige, em linguagem simples: todo evento que muda o estoque — entrou, saiu, voltou, foi pra outro local, foi ajustado, se perdeu ou foi descartado — precisa virar um registro imutável no histórico (ledger). Ninguém pode "editar" ou "apagar" um movimento depois de gravado; qualquer correção é um NOVO movimento.

Como funciona
A tabela inventory.movements (model InventoryMovement) só recebe INSERT — não existe nenhuma rota/serviço de UPDATE ou DELETE sobre um movimento já gravado em todo src/features/inventory/. Os 7 tipos exigidos pelo Caderno estão todos implementados na constante MOVEMENT_TYPES = ['IN', 'OUT', 'RETURN', 'TRANSFER', 'ADJUSTMENT', 'LOSS', 'DISPOSAL'] de movements.service.js. Três deles (ADJUSTMENT, LOSS, DISPOSAL) exigem a permissão inventory:approve por alterarem saldo sem uma origem física rastreável automaticamente (mesmo padrão de alçada usado em construction:approve/finance:approve), além de motivo (reason) sempre obrigatório e evidência obrigatória acima de um limiar de valor/risco configurável (REG-EST-002, Motor de Regras). Cada linha grava movedByUserId/createdBy não-nulos (autor sempre rastreável) e nunca é reaproveitada: todo recordMovement sempre faz um InventoryMovement.create novo (exceto no caminho de idempotência, que devolve o registro já existente em vez de criar duplicata — ver EST-TS-12 abaixo).

EST-003 — Saldo nunca é digitado manualmente; deriva do ledger de forma transacionalmente consistente

Resolvido

O que o Caderno exige, em linguagem simples: ninguém pode simplesmente "escrever" um número de saldo no sistema. O saldo de cada item em cada local é sempre o resultado matemático da soma de todos os movimentos daquele item/local — e essa soma precisa ser calculada de forma segura mesmo com várias pessoas mexendo ao mesmo tempo.

Como funciona
Existe exatamente UMA função no sistema inteiro que escreve em inventory.stock_balances: applyBalanceDelta, dentro de movements.service.js — nenhum controller, rota ou outro service tem acesso de escrita direto a essa tabela. Toda vez que um movimento é gravado, applyBalanceDelta busca a linha de saldo com lock: transaction.LOCK.UPDATE (FOR UPDATE), soma/subtrai o delta, e bloqueia se o resultado for negativo e o item não permitir estoque negativo (INVENTORY_INSUFFICIENT_BALANCE). O lock de linha serializa concorrência real: duas saídas simultâneas do mesmo item/local disputam a mesma linha de stock_balances e o Postgres força uma a esperar a outra committar — só depois ela lê o saldo já atualizado (ver teste de concorrência EST-TS-02 abaixo, que intercepta deliberadamente o ponto do lock para provar isso sob corrida real, não só sequencialmente). Para TRANSFER, os dois lados (saída da origem, entrada no destino) acontecem na MESMA transação, então nunca existe um estado intermediário onde o saldo "sumiu" de um lado sem aparecer no outro.
Código real
// EST-002: saldo é sempre derivado de movimentos, nunca digitável diretamente — esta é a
// ÚNICA função do sistema que deve escrever em inventory.stock_balances.
async function applyBalanceDelta(inventoryItemId, locationId, delta, companyId, groupId, allowNegativeStock, transaction) {
  let balance = await InventoryStockBalance.findOne({
    where: { inventoryItemId, locationId, groupId, companyId },
    transaction,
    lock: transaction.LOCK.UPDATE,
  });
  if (!balance) {
    balance = await InventoryStockBalance.create(
      { groupId, companyId, inventoryItemId, locationId, quantityOnHand: 0 },
      { transaction }
    );
  }
  const nextQuantity = Number(balance.quantityOnHand) + Number(delta);
  if (nextQuantity < 0 && !allowNegativeStock) {
    throw AppError.badRequest(
      `Saldo insuficiente no local informado (disponível: ${balance.quantityOnHand}, solicitado: ${Math.abs(delta)}).`,
      'INVENTORY_INSUFFICIENT_BALANCE'
    );
  }
  balance.quantityOnHand = nextQuantity;
  await balance.save({ transaction });
  return balance;
}

EST-004 — Material consumido na obra precisa de project_id/stage_id

Resolvido

O que o Caderno exige, em linguagem simples: sempre que um material sai (ou entra) de um local que é "de obra" (canteiro), o movimento precisa saber de qual obra e, se aplicável, de qual etapa ele é — senão o custo daquele material nunca consegue ser atribuído corretamente à obra certa.

Como funciona
A validação acontece em DOIS pontos complementares. (1) Na camada mais baixa, recordMovement (movements.service.js) verifica se qualquer local tocado (origem ou destino) é do tipo PROJECT_SITE; se for e projectId não foi informado, lança INVENTORY_MOVEMENT_PROJECT_REQUIRED — essa é a barreira que vale para QUALQUER caminho de criação de movimento (manual, requisição, recebimento), não só a tela de requisições. (2) Na camada de requisição (requisitions.service.js#createRequisition), a validação é bidirecional: se vier projectId sem projectLocationId é bloqueado, e se vier projectLocationId apontando pra um local PROJECT_SITE sem projectId também é bloqueado (REQUISITION_PROJECT_LOCATION_REQUIRES_PROJECT) — essa segunda direção foi um gap real encontrado e corrigido em auditoria (sem ela, seria possível criar requisição apontando pro canteiro sem vínculo de obra, e o OUT gerado depois sairia com projectId: null). Quando há stageId, ele precisa pertencer à MESMA obra informada (ProjectStage.findOne({ where: { id: stageId, projectId } })) — stage de outra obra é recusado com INVENTORY_REQUISITION_STAGE_INVALID.

EST-009 — Nota fiscal/documento de entrada vinculado à compra/recebimento (Seção 6, Entrada por NF)

Resolvido

O que o Caderno exige, em linguagem simples: todo recebimento de material nasce de um documento real (nota fiscal/foto), e esse documento fica permanentemente ligado ao recebimento — não é só um texto digitado, é um arquivo rastreável guardado no sistema. O fluxo é: DRAFT (cadastro) → REVIEWED (conferido por um humano) → COMPLETED (confirmado, atualiza saldo e custo).

Como funciona
O recebimento é a tabela inventory.receipts (model InventoryReceipt), com invoiceFileId (referência a File, o módulo de arquivos central do sistema), invoiceNumber e invoiceFingerprint (hash/chave de deduplicação da NF). O ciclo de vida é uma máquina de estados estrita: createReceipt só cria em DRAFT; reviewReceipt só transiciona DRAFT → REVIEWED (rejeita qualquer outro estado origem com INVENTORY_RECEIPT_INVALID_TRANSITION); confirmReceipt só transiciona REVIEWED → COMPLETED, e é esse último passo — e só ele — que chama recordMovement com movementType: 'IN' pra cada linha do recebimento, atualizando saldo real. O campo de OCR/IA (receiptOcr.service.js) entra ANTES da confirmação: sugere itens/quantidades/preços a partir do documento, mas é o usuário humano que confere e ajusta antes de confirmar — o service de confirmação não reexecuta OCR nem confia cegamente na sugestão, ele só processa o que está persistido em InventoryReceiptItem no momento da chamada.

EST-011 — Custo médio/FIFO na obra, nunca duplicado no Financeiro

Resolvido

O que o Caderno exige, em linguagem simples: o custo do material usado na obra tem que vir de uma política de custo definida (custo médio, neste caso) — nunca um valor "chutado" na hora — e esse custo não pode ser lançado duas vezes no Financeiro (uma vez pelo Estoque, outra pelo módulo financeiro de obra).

Como funciona
A política adotada é custo médio ponderado (weighted average cost). O único ponto do código que escreve em InventoryItem.averageCost é dentro de confirmReceipt (receipts.service.js) — nenhum outro service grava nessa coluna. O cálculo soma o saldo total ANTES de aplicar a entrada desta linha (pra não contaminar o próprio denominador com a entrada que está sendo processada): averageCost = (saldoTotalAntes × custoMédioAntigo + quantidadeRecebida × custoDaNF) / (saldoTotalAntes + quantidadeRecebida). O acesso é protegido por lock: transaction.LOCK.UPDATE na linha do item, serializando confirmações concorrentes do mesmo item. Quanto à "não duplicação no Financeiro": o Estoque nunca cria um FinancialEntry diretamente a partir de um recebimento/requisição de consumo — o custo chega à Obra via evento de domínio (outbox), e é o módulo financeiro/Obras quem decide o que fazer com esse dado, sem o Estoque duplicar o lançamento. O único caso em que o módulo de Estoque de fato cria um FinancialEntry é a venda/baixa de patrimônio (Gap 3, §9 do Caderno), e lá existe uma idempotencyKey dedicada (asset-disposal:{assetId}) que é inclusive protegida contra reuso por outras operações (transferAsset recusa explicitamente uma idempotencyKey com esse prefixo reservado), evitando duplicidade mesmo nesse caso excepcional.
Código real

EST-TS-12 — Evento repetido é idempotente (reenvio/retry não duplica)

Resolvido

O que o Caderno exige, em linguagem simples: se a mesma operação chegar duas vezes no sistema (por exemplo, por causa de um retry de rede), ela não pode ser executada duas vezes — tem que ser reconhecida como "a mesma" e devolvida sem duplicar nada.

Como funciona
A idempotência existe em dois níveis complementares. (1) Nível de domínio: todo movimento gerado por um fluxo de negócio (recebimento, requisição) carrega uma idempotencyKey determinística (ex.: receipt:{receiptId}:item:{lineId}, req:{requisitionId}:item:{lineId}). Dentro de recordMovement, antes de criar qualquer coisa, o código busca por um movimento já existente com essa chave na empresa; se existir, devolve o registro ORIGINAL em vez de criar um novo — mesmo que a contagem física tenha sido aberta entre a primeira chamada e o reenvio, o caminho idempotente responde ANTES da checagem de freeze lógico (§10), porque reenviar algo que já aconteceu antes da contagem abrir não é um "novo" movimento sujeito ao freeze. (2) Nível de evento de domínio: todo evento publicado via publishDomainEvent (Transactional Outbox, outbox.js) exige uma idempotencyKey obrigatória (coluna UNIQUE em integration.outbox_events) — sem ela, a própria função lança OUTBOX_IDEMPOTENCY_KEY_MISSING antes de gravar qualquer coisa. O evento inventory.receipt.completed, por exemplo, usa a chave inventory.receipt.completed:{receiptId} — reenviar a publicação do mesmo recebimento não cria uma segunda linha na outbox.

Resolvido

O que o Caderno exige, em linguagem simples: o Caderno lista 5 riscos de fraude específicos do módulo de Estoque/Patrimônio/Compras e o controle exigido para cada um. Abaixo, cada risco é mapeado para o mecanismo real do código que o neutraliza.

Baixa sem retirada → QR/responsável/evidência

Compras (Procurement) e Fornecedores

5/8 resolvidos · 3 parciais

Fluxo completo REQUEST → APPROVAL → RFQ → COMPARISON → AWARD → PO → RECEIPT → MATCH → PAYABLE

Resolvido

O que o Caderno exige, em linguagem simples: uma compra precisa passar por um funil formal, nunca "pular etapa" — alguém pede o material, outra pessoa aprova a necessidade, o comprador manda cotar com fornecedores, o sistema compara as ofertas, alguém adjudica a vencedora virando um Pedido de Compra (PO), o PO é recebido fisicamente, o recebimento é conferido contra o PO, e só então nasce o contas a pagar do fornecedor. Cada etapa só pode nascer da etapa anterior, no estado certo.

Como funciona
O fluxo é literalmente modelado assim em procurement.service.js: createPurchaseRequest (REQUEST, status REQUESTED) → decidePurchaseRequest (APPROVAL, vira APPROVED/REJECTED, com segregação "quem cria não aprova" fail-closed) → createQuotation (RFQ, cria/reaproveita uma Quotation OPEN idempotente por requisição) → submitSupplierOffer (fornecedores respondem com SupplierOffer/SupplierOfferItem) → compareOffers (COMPARISON, somente leitura, ordena por totalAmount e já traz o nome do fornecedor) → awardSupplierOffer (AWARD, fecha a Quotation, marca a requisição AWARDED e cria o PurchaseOrder + PurchaseOrderItem, status OPEN) → confirmGoodsReceipt (RECEIPT, delega a baixa física real a inventory.receipts, nunca duplica a lógica de IN/saldo) → three-way match embutido na mesma função (MATCH, PO x quantidade recebida x valor da NF) → geração do FinancialEntry nature PAYABLE (PAYABLE), idempotente por goodsReceipt.id. Cada transição tem uma guarda de estado explícita (ex.: só pode abrir cotação de requisição APPROVED; só pode adjudicar oferta RECEIVED de uma Quotation ainda OPEN; só pode receber PO OPEN) que lança AppError com código de negócio quando violada.

Three-way match (PO x recebimento x nota fiscal) e abertura de divergência

Resolvido

O que o Caderno exige, em linguagem simples: antes de pagar um fornecedor, o sistema precisa bater três números — o que foi pedido no PO, o que chegou fisicamente, e o que a nota fiscal está cobrando. Se algum desses três não bater (quantidade a mais, valor diferente), isso não pode virar um pagamento automático silencioso — precisa abrir um "caso" formal para um humano decidir.

Como funciona

Se invoiceTotalAmount foi informado e diverge do valor esperado (soma de unitPrice × receivedQty capada ao saldo do PO) além da tolerância de 1 centavo, abre PRICE_MISMATCH. No cancelamento de um PO com saldo não recebido, abre UNDER_RECEIPT. As três cobrem as três pontas do three-way match: quantidade recebida vs. PO (over/under) e valor da NF vs. PO×quantidade (price). Toda discrepância nasce status: 'OPEN' e só é fechada por resolveDiscrepancy (ACCEPTED/REJECTED), que tem consequência financeira real: rejeitar um PRICE_MISMATCH estorna o payable errado e cria um corrigido pelo valor esperado; aceitar um OVER_RECEIPT cria um payable adicional só pelo valor do excedente (o excedente nunca entra automaticamente no contas a pagar — fica capado até decisão humana).

PO duplicado e cancelamento idempotente com compensação (segregação de alçada incluída)

Resolvido

O que o Caderno exige, em linguagem simples: não pode existir dois Pedidos de Compra nascidos da mesma oferta/cotação por acidente (duplo clique, corrida de concorrência), e cancelar um PO precisa deixar rastro formal do que não vai mais chegar — nunca sumir com o saldo pendente silenciosamente, e nunca deixar a empresa devendo um pagamento de uma compra que o próprio sistema marcou como cancelada.

Como funciona
PO duplicado é bloqueado em duas camadas: (1) createQuotation reaproveita a Quotation OPEN existente da mesma requisição sob lock pessimista (nunca cria uma segunda cotação-irmã); (2) awardSupplierOffer valida o status da Quotation (não só da SupplierOffer) — uma cotação já CLOSED (adjudicada) rejeita qualquer segunda tentativa de adjudicar outra oferta da mesma cotação com QUOTATION_ALREADY_AWARDED, mesmo que essa segunda oferta ainda esteja RECEIVED. Cancelamento (cancelPurchaseOrder) é permitido em PO OPEN ou RECEIVED; para cada item com saldo não recebido, abre uma ReceiptDiscrepancy UNDER_RECEIPT (a "compensação" exigida pelo contrato); se já existe GoodsReceipt com financialEntryId (payable já criado, possivelmente já SETTLED), esse FinancialEntry é estornado via reverseFinancialEntry — nunca editado (FIN-010). Status CANCELED bloqueia recancelar.

Receipt replay e over-receipt — idempotência de recebimento sob concorrência e retry

Resolvido

O que o Caderno exige, em linguagem simples: se a mesma requisição de recebimento for reenviada (rede instável, duplo clique, retry automático), isso nunca pode gerar um segundo recebimento nem um segundo pagamento. E se chegou fisicamente mais material do que o PO previa, isso precisa ser sinalizado, nunca aceito como se fosse normal.

Como funciona
Duas camadas de proteção contra replay: (1) invoiceFingerprint — se informado, um GoodsReceipt com a mesma NF já existente na empresa bloqueia a segunda tentativa com GOODS_RECEIPT_DUPLICATE_INVOICE; a checagem roda DEPOIS do lock FOR UPDATE do PO, serializando duas chamadas concorrentes (TOCTOU corrigido — a segunda só lê depois do commit da primeira). (2) idempotencyKey opcional do cliente — essencial para recebimento PARCIAL, onde o PO continua OPEN e por isso o status do PO sozinho não protege contra duplo processamento; se a chave já foi usada, a função retorna o GoodsReceipt já existente em vez de criar um novo. Over-receipt (ver item 3) sempre abre ReceiptDiscrepancy OVER_RECEIPT e capa a contribuição financeira do excedente no payable automático — o excedente só vira pagável se um humano aceitar explicitamente via resolveDiscrepancy.

function addDaysDateOnly(dateOnlyStr, days) {
