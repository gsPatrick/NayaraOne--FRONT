Persistência de obras, etapas, prazos, progresso, custos, responsáveis e dependências

Resolvido

O que a Nayara pediu, em linguagem simples: o sistema precisa guardar de verdade, no banco de dados, todos os dados de uma obra — nome, prazos, quem é o responsável, em que etapa está, quanto já foi feito (progresso), quanto custa e quais etapas dependem de quais. Nada disso pode ser "calculado na hora" ou existir só na tela — tem que estar persistido e recuperável depois.

Como funciona
A obra é a tabela construction.projects (model Project), com código único gerado automaticamente no formato OBRA-{ANO}-{SEQ:04d} (ex.: OBRA-2026-0001) através de um INSERT...ON CONFLICT...DO UPDATE atômico protegido por pg_advisory_xact_lock (nunca um SELECT COUNT(*)+1, que teria corrida de concorrência). Cada obra tem budgetAmount, startsAt/endsAtPlanned/actualEndDate, responsibleUserId e status. Etapas (construction.project_stages, model ProjectStage) pertencem a uma obra (projectId) e guardam plannedPct/measuredPct (progresso planejado vs. medido), plannedCost, startsAt/endsAt e sequence. Dependências entre etapas vivem em tabela própria (construction.stage_dependencies, ver item 2). Toda criação/edição passa por validação de tipo numérico (Number.isFinite, nunca aceita NaN/Infinity que o Postgres aceitaria silenciosamente em colunas NUMERIC) e de data (Number.isNaN(new Date(x).getTime())), lançando AppError.badRequest com código de negócio antes de qualquer INSERT. Toda operação é auditada via registrarAuditoria (before/after JSON), e o responsável (createdBy/updatedBy) é sempre gravado.

async function generateProjectCode(companyId, transaction) {
  const year = new Date().getFullYear();
  const lockKey = `${companyId}:${year}`;
  await sequelize.query('SELECT pg_advisory_xact_lock(hashtextextended(:lockKey, 0))', { replacements: { lockKey }, transaction });
  const [rows] = await sequelize.query(
    `INSERT INTO "construction"."project_code_sequences" (id, company_id, "year", last_seq, created_at, updated_at)
     VALUES (gen_random_uuid(), :companyId, :year, 1, now(), now())
     ON CONFLICT (company_id, "year")
     DO UPDATE SET last_seq = "construction"."project_code_sequences".last_seq + 1, updated_at = now()
     RETURNING last_seq`,
    { replacements: { companyId, year }, transaction }
  );
  const seq = rows[0].last_seq;
  return `OBRA-${year}-${String(seq).padStart(4, '0')}`;
}

Bloqueio de ciclos indiretos entre etapas

Resolvido

O que a Nayara pediu, em linguagem simples: se a etapa "Estrutura" depende da "Fundação", e a "Alvenaria" depende da "Estrutura", ninguém pode depois fazer a "Fundação" depender da "Alvenaria" — isso criaria um ciclo impossível de executar (A espera B, que espera C, que espera A). O sistema precisa impedir isso mesmo quando o ciclo não é direto, mas passa por várias etapas no meio.

Como funciona
Toda dependência fica na tabela construction.stage_dependencies (model StageDependency, campos stageId/dependsOnStageId). Antes de inserir uma nova aresta "X depende de Y", o sistema roda uma busca em profundidade (DFS, função wouldCreateCycle) partindo de Y e seguindo todas as arestas "depende de" já existentes no banco — se esse caminho alcançar X, significa que Y já depende (direta ou indiretamente) de X, e criar "X depende de Y" fecharia um ciclo; a operação é bloqueada com AppError.badRequest('...dependência circular', 'STAGE_DEPENDENCY_CYCLE'). Para não ter corrida de concorrência (duas requisições criando as arestas opostas ao mesmo tempo, nenhuma vendo a aresta da outra ainda), todo createStageDependency do mesmo projeto é serializado por pg_advisory_xact_lock ANTES do DFS — só uma transação por vez entra na seção crítica daquele grafo. Além disso, valida auto-referência (etapa não pode depender de si mesma) e que as duas etapas pertencem à MESMA obra (dependência de sequenciamento não faz sentido entre obras diferentes).
Código real
async function wouldCreateCycle(stageId, dependsOnStageId, transaction) {
  const visited = new Set();
  const stack = [dependsOnStageId];
  while (stack.length > 0) {
    const current = stack.pop();
    if (current === stageId) return true;
    if (visited.has(current)) continue;
    visited.add(current);
    const edges = await StageDependency.findAll({ where: { stageId: current }, transaction });
    for (const edge of edges) {
      if (!visited.has(edge.dependsOnStageId)) stack.push(edge.dependsOnStageId);
    }
  }
  return false;
}

async function createStageDependency(stageId, payload, actorUserId, transaction) {
  const { groupId, companyId, dependsOnStageId } = payload;
  if (!groupId || !companyId || !dependsOnStageId) {
    throw AppError.badRequest('...obrigatórios.', 'STAGE_DEPENDENCY_VALIDATION');
  }
  if (stageId === dependsOnStageId) {
    throw AppError.badRequest('Uma etapa não pode depender de si mesma.', 'STAGE_DEPENDENCY_SELF_REFERENCE');
  }
  // ... valida existência e mesma obra (dependsOnStage.projectId !== stage.projectId -> CROSS_PROJECT)
  const lockKey = `stage_dependency:${stage.projectId}`;
  await sequelize.query('SELECT pg_advisory_xact_lock(hashtextextended(:lockKey, 0))', { replacements: { lockKey }, transaction });
  const existing = await StageDependency.findOne({ where: { stageId, dependsOnStageId }, transaction });
  if (existing) throw AppError.conflict('Essa dependência já existe.', 'STAGE_DEPENDENCY_DUPLICATE');
  const createsCycle = await wouldCreateCycle(stageId, dependsOnStageId, transaction);
  if (createsCycle) {
    throw AppError.badRequest('Esta dependência criaria um ciclo entre etapas (dependência circular).', 'STAGE_DEPENDENCY_CYCLE');
  }
  const dependency = await StageDependency.create({ groupId, companyId, stageId, dependsOnStageId, ... }, { transaction });
  // ... auditoria
  return dependency;
}

Todas as transições de estado previstas, inclusive PAUSED durante ACTIVE, e bloqueio de transições inválidas

Resolvido

O que a Nayara pediu, em linguagem simples: uma obra passa por fases bem definidas (planejada → orçada → pronta → em execução → inspeção final → entregue → garantia → encerrada), e em qualquer momento pode ser cancelada. Durante a execução, a obra também pode ser pausada e depois retomada. O sistema não pode deixar ninguém "pular etapas" nem voltar para trás de forma inválida — só os caminhos previstos.

Como funciona
Os 10 estados (PLANNED, BUDGETED, READY, ACTIVE, PAUSED, FINAL_INSPECTION, DELIVERED, WARRANTY, CLOSED, CANCELLED) estão todos na constante STATUSES, e o grafo de transições válidas está em VALID_TRANSITIONS. A função genérica transitionProject usa lock pessimista (transaction.LOCK.UPDATE) na linha da obra antes de ler o status atual — isso impede que duas transições concorrentes a partir do mesmo status (ex.: ACTIVE→PAUSED numa aba e ACTIVE→CANCELLED em outra) leiam o mesmo estado de origem antes de uma delas commitar. Em seguida checa se o status alvo está em VALID_TRANSITIONS[statusAtual]; se não estiver, lança AppError.conflict(..., 'PROJECT_STATUS_TRANSITION_INVALID'). DELIVERED, WARRANTY e CLOSED são propositalmente OMITIDOS de VALID_TRANSITIONS — só são alcançáveis pelos gates dedicados deliverProject/closeProjectWarranty, que verificam não conformidade crítica / casos de garantia abertos antes de avançar. Da mesma forma, BUDGETED só é alcançável de verdade por approveBudget() (nunca pela transição genérica), porque exige margem mínima validada e baseline congelada. READY→ACTIVE também tem um gate extra: exige orçamento, datas e responsável preenchidos, lançando PROJECT_MISSING_REQUIRED_FIELDS se faltar algum.

const VALID_TRANSITIONS = {
  PLANNED: ['CANCELLED'],
  BUDGETED: ['READY', 'CANCELLED'],
  READY: ['ACTIVE', 'CANCELLED'],
  ACTIVE: ['PAUSED', 'FINAL_INSPECTION', 'CANCELLED'],
  PAUSED: ['ACTIVE', 'CANCELLED'],
  FINAL_INSPECTION: ['ACTIVE', 'CANCELLED'],
  DELIVERED: [], WARRANTY: [], CLOSED: [], CANCELLED: [],
};

async function transitionProject(id, targetStatus, actorUserId, transaction) {
  const project = await Project.findByPk(id, { transaction, lock: transaction ? transaction.LOCK.UPDATE : undefined });
  if (!project) throw AppError.notFound('Obra não encontrada.', 'PROJECT_NOT_FOUND');
  const normalizedTarget = String(targetStatus || '').toUpperCase();
  if (!STATUSES.includes(normalizedTarget)) {
    throw AppError.badRequest(`"targetStatus" deve ser um de: ${STATUSES.map(statusLabelPt).join(', ')}.`, 'PROJECT_STATUS_INVALID');
  }
  const allowed = VALID_TRANSITIONS[project.status] || [];
  if (!allowed.includes(normalizedTarget)) {
    throw AppError.conflict(`Não é possível mover a obra de "${statusLabelPt(project.status)}" para "${statusLabelPt(normalizedTarget)}".`, 'PROJECT_STATUS_TRANSITION_INVALID');
  }
  if (project.status === 'READY' && normalizedTarget === 'ACTIVE') {
    const missing = [];
    if (project.budgetAmount == null) missing.push('orçamento (budgetAmount)');
    if (!project.startsAt) missing.push('data de início (startsAt)');
    if (!project.endsAtPlanned) missing.push('previsão de término (endsAtPlanned)');
    if (!project.responsibleUserId) missing.push('responsável (responsibleUserId)');
    if (missing.length > 0) throw AppError.badRequest(`Não é possível iniciar a execução da obra sem: ${missing.join(', ')}.`, 'PROJECT_MISSING_REQUIRED_FIELDS');
  }
  const fromStatus = project.status;
  project.status = normalizedTarget;
  if (normalizedTarget === 'FINAL_INSPECTION' && !project.actualEndDate) {
    project.actualEndDate = new Date().toISOString().slice(0, 10);
  }
  await project.save({ transaction });
  await publishProjectStatusChanged(project, fromStatus, transaction);
  // ... auditoria
  return project;
}

Criação, persistência e totalização de itens orçamentários

Resolvido

O que a Nayara pediu, em linguagem simples: o orçamento de uma obra é feito de várias linhas (fundação, estrutura, acabamento etc.), cada uma com seu valor planejado. O sistema precisa guardar cada linha separadamente e depois somar tudo certo na hora de fechar o orçamento total da obra.

Como funciona
Cada linha fica em construction.budget_lines (model BudgetLine), com category, description, plannedAmount e actualAmount (este último sempre null na criação — nunca digitado, ver item 8). A validação assertNonNegativeAmount usa Number.isFinite (não só Number.isNaN) para rejeitar também o valor especial Infinity, que o Postgres aceitaria silenciosamente numa coluna NUMERIC. A totalização agregada acontece em approveBudget (budgets.service.js): busca TODAS as BudgetLine vinculadas ao budgetId via BudgetLine.findAll e soma com reduce sobre Number(line.plannedAmount || 0) — nunca um valor digitado solto no corpo da requisição de aprovação. Esse total vira budget.totalAmount e budget.baselineAmount (a baseline congelada, ver item 5) no mesmo momento, dentro da mesma transação com lock pessimista no Budget.

function assertNonNegativeAmount(value, fieldName) {
  if (value === undefined || value === null) return;
  const numeric = Number(value);
  if (!Number.isFinite(numeric)) {
    throw AppError.badRequest(`"${fieldName}" deve ser numérico.`, 'BUDGET_LINE_VALIDATION');
  }
  if (numeric < 0) {
    throw AppError.badRequest(`"${fieldName}" não pode ser negativo.`, 'BUDGET_LINE_VALIDATION');
  }
}

Imutabilidade da baseline aprovada por tela e API

Resolvido

O que a Nayara pediu, em linguagem simples: depois que o orçamento de uma obra é aprovado, ninguém pode simplesmente editar os valores (nem pela tela, nem direto pela API) para "ajustar" o orçamento — isso destruiria a confiabilidade da baseline. Fluxo completo de Change Order, incluindo motivo, descrição, impactos financeiros e de prazo, evidências, aprovação, rejeição e efeitos sobre a baseline

Resolvido

O que a Nayara pediu, em linguagem simples: quando aparece um imprevisto na obra que muda o escopo (ex.: "precisou reforçar a fundação"), isso precisa virar um pedido formal de mudança — com motivo, descrição, quanto isso custa a mais, quantos dias atrasa, e fotos/documentos de evidência. Alguém aprova ou rejeita esse pedido, e só quando aprovado é que o orçamento da obra muda de verdade.

Como funciona
Cada Change Order (construction.change_orders, model ChangeOrder) tem reasonCode, description, budgetImpact (pode ser positivo ou negativo), scheduleImpactDays e evidenceFileIds (lista de arquivos). Nasce sempre em PENDING_APPROVAL (não existe endpoint de "submeter" separado do de criar). A decisão (decideChangeOrder) usa lock pessimista no próprio Change Order — duas decisões simultâneas não podem ambas passar pela checagem de status pendente. Se REJECT: só muda o status para REJECTED, nada no orçamento é tocado (prova real no teste "Change Order rejeitado não altera o orçamento"). Se APPROVE: exige que a obra já tenha um Budget com status === 'APPROVED' (senão CHANGE_ORDER_NO_APPROVED_BUDGET) — Change Order não cria baseline do zero, só ajusta uma já existente. O novo baseline é budget.baselineAmount + changeOrder.budgetImpact (bloqueia se o resultado ficar negativo: CHANGE_ORDER_NEGATIVE_RESULT), e essa é a ÚNICA forma de alterar um orçamento já aprovado — todo o resto do sistema bloqueia essa edição (ver item 5). A aprovação também sincroniza project.budgetAmount com o novo baseline, na mesma transação, com lock pessimista no Project também — sem isso, o campo que o resto do sistema lê como "orçamento oficial" ficaria desatualizado depois do primeiro Change Order aprovado (bug real corrigido, documentado no código).

  const decision = String(payload && payload.decision ? payload.decision : '').toUpperCase();
  if (!['APPROVE', 'REJECT'].includes(decision)) {
    throw AppError.badRequest('"decision" deve ser "APPROVE" ou "REJECT".', 'CHANGE_ORDER_DECISION_INVALID');
  }
  const changeOrder = await ChangeOrder.findByPk(id, { transaction, lock: transaction ? transaction.LOCK.UPDATE : undefined });
  if (!changeOrder) throw AppError.notFound('Change Order não encontrado.', 'CHANGE_ORDER_NOT_FOUND');
  if (changeOrder.status !== 'PENDING_APPROVAL') { /* ...CHANGE_ORDER_NOT_PENDING */ }

  if (decision === 'REJECT') {
    changeOrder.status = 'REJECTED';
    changeOrder.decidedBy = actorUserId || null;
    changeOrder.decidedAt = new Date();
    await changeOrder.save({ transaction });
    // ... auditoria, retorna sem tocar no Budget
    return changeOrder;
  }

  const budget = await Budget.findOne({ where: { projectId: changeOrder.projectId }, transaction, lock: transaction ? transaction.LOCK.UPDATE : undefined });
  if (!budget || budget.status !== 'APPROVED') {
    throw AppError.conflict('Só é possível aprovar Change Order de obra com orçamento já aprovado (baseline existente).', 'CHANGE_ORDER_NO_APPROVED_BUDGET');
  }
  const newBaseline = Number(budget.baselineAmount) + Number(changeOrder.budgetImpact);
  if (newBaseline < 0) throw AppError.badRequest('Aplicar este Change Order deixaria o orçamento com valor negativo.', 'CHANGE_ORDER_NEGATIVE_RESULT');
  budget.baselineAmount = newBaseline;
  budget.totalAmount = newBaseline;
  await budget.save({ transaction });

  const project = await Project.findByPk(changeOrder.projectId, { transaction, lock: transaction ? transaction.LOCK.UPDATE : undefined });
  if (project) { project.budgetAmount = newBaseline; await project.save({ transaction }); }

  changeOrder.status = 'APPROVED';
  changeOrder.decidedBy = actorUserId || null;
  changeOrder.decidedAt = new Date();
  await changeOrder.save({ transaction });
  return changeOrder;
}

Preenchimento e persistência de todos os campos do RDO

Resolvido

O que a Nayara pediu, em linguagem simples: O Relatório Diário de Obra (RDO) precisa capturar, salvar e preservar TODOS os dados de um dia de trabalho — clima, efetivo (quantidade de pessoas), ocorrências, serviços executados, equipe, materiais e fotos — sem perder informação quando alguém corrige um RDO já enviado, e sem permitir que o mesmo dia/turno seja cadastrado duas vezes por engano.

Como funciona
O RDO é persistido na tabela construction.daily_reports (model DailyReport), com duas tabelas filhas: daily_workers (equipe do dia) e daily_materials (materiais usados no dia). A função createDailyReport (src/features/construction/dailyReports.service.js, linha 132) valida na ordem:
  1. Campos obrigatórios (groupId, companyId, reportDate) — rejeita com DAILY_REPORT_VALIDATION se ausentes.
  2. reportDate precisa ser uma data válida (Number.isNaN(new Date(reportDate).getTime())) — corrige um bug onde uma data malformada ia direto pro banco.
  3. workforceCount, se enviado, precisa ser um número finito ≥ 0 (validateWorkforceCount) — rejeita NaN/Infinity/negativo com DAILY_REPORT_WORKFORCE_INVALID.
  4. Idempotência por idempotencyKey (app offline reenviando o mesmo RDO): se já existe um registro com essa chave, devolve o registro existente em vez de duplicar ou dar erro de conflito.
  5. Chave lógica (project_id, report_date, shift_code): se já existe um RDO para a mesma obra/data/turno, lança AppError.conflict(..., 'DAILY_REPORT_DUPLICATE') — mas turnos diferentes no mesmo dia são permitidos (ex.: MANHÃ e TARDE).
Dentro de replaceDailyMaterials (linha 94), cada material exige materialDescription, quantity (também validado com Number.isFinite e ≥ 0 — bug real corrigido: o banco é DECIMAL(14,4) e o Postgres aceita literalmente o valor especial 'NaN'/'Infinity', então sem esse guard o INSERT nunca falhava e dado corrompido entrava silenciosamente) e unit.

Correção de RDO é append-only, nunca UPDATE in-place: correctDailyReport (linha 313) cria uma linha NOVA com supersedesId apontando para o registro anterior — o original nunca é alterado nem apagado. getCurrentDailyReport (linha 273) segue a cadeia supersedesId para sempre devolver a revisão mais recente; getDailyReportHistory (linha 294) devolve a cadeia inteira, da mais antiga à mais nova, para a tela mostrar o histórico de correções. Um bug real corrigido nesta rodada: um PATCH parcial que só reenvia, por exemplo, occurrences/workforceCount (sem reenviar workers/materials) antes criava uma revisão SEM equipe/materiais, porque as funções de substituição são no-op quando o campo não é array — agora, quando o campo não é reenviado, a revisão copia as linhas da revisão anterior (linhas 346-351).

O que a Nayara pediu, em linguagem simples: Cada trabalhador que aparece no diário de obra precisa estar de fato vinculado a um cadastro real de Pessoa (PF) ou Fornecedor no sistema — não pode ser só um nome digitado em texto livre — e precisa ser possível anexar a documentação correspondente daquele prestador (ex.: contrato, ASO, documento de identidade) a cada entrada do diário.

Como funciona
A equipe do dia é gravada na tabela construction.daily_workers (model DailyWorker), uma linha por trabalhador por RDO, com FK obrigatória para people.id (cadastro de Pessoa/Fornecedor do módulo de Pessoas). A função replaceDailyWorkers (dailyReports.service.js, linha 67) é chamada tanto na criação quanto na correção do RDO:
  1. Apaga (hard delete, force: true) todas as linhas de equipe anteriores daquele RDO específico — é uma SUBSTITUIÇÃO completa do conjunto, não um merge incremental.
  2. Para cada item da lista workers, exige personId — se ausente, lança AppError.badRequest(..., 'DAILY_WORKER_VALIDATION'). Isso é o que garante o vínculo real: não existe caminho para gravar um trabalhador "texto livre" sem personId apontando para um registro de Pessoa já existente (a FK do banco reforça isso no nível físico).
  3. role (função do trabalhador no dia) é opcional.
  4. documentFileIds — array de IDs de arquivo (upload prévio via files.service.js) — representa a documentação daquele prestador específico naquele dia. Se não enviado, grava array vazio (nunca null, para o Op.overlap/checagens de ausência funcionarem de forma previsível).
Essas mesmas linhas de documentFileIds são a entrada do job de detecção de ausência de documentação (ver item 4 abaixo) — detectMissingWorkerDocuments varre DailyWorker.documentFileIds com [Op.or]: [{ documentFileIds: [] }, { documentFileIds: null }] para achar trabalhadores sem documentação anexada numa janela de 7 dias.

Um gap real corrigido nesta auditoria (achado numa varredura do Front, 30/09/2026): não existia NENHUM endpoint para LER a equipe/materiais já salvos de um RDO existente — só a gravação interna (replaceDailyWorkers) existia, então editar um RDO não conseguia mostrar a equipe/documentação já cadastrada. Corrigido com listDailyWorkers (linha 253) e listDailyMaterials (linha 259), ambos expostos como consultas simples por dailyReportId.

  if (!Array.isArray(workers)) return;

        createdBy: actorUserId || null,
        updatedBy: actorUserId || null,
      },
      { transaction }
    );
  }
}

Integridade e origem das fotos por hash; detecção de reutilização suspeita de fotos

Resolvido

O que a Nayara pediu, em linguagem simples: As fotos anexadas ao diário de obra precisam ter uma "impressão digital" de integridade (hash) que prove que o conteúdo não foi alterado depois do upload, e o sistema precisa alertar quando a MESMA foto (mesmo conteúdo, não necessariamente o mesmo arquivo) aparece reaproveitada em mais de um RDO — um sinal de que alguém pode estar reciclando foto antiga para simular um dia de trabalho que não aconteceu.

Como funciona
Hash/origem: todo upload de arquivo (files.service.js) já calcula e grava File.checksumSha256 no momento do upload — essa é a prova de integridade de conteúdo, nunca recalculada depois.

Reuso suspeito (GAP fechado nesta sessão): a checagem de reuso por hash (detectEvidenceReuse, M6-59) já existia em nonconformities.service.js, mas nunca tinha sido conectada ao Diário de Obra — apesar do RDO também gravar evidenceFileIds. Em vez de duplicar a lógica de comparação de hash, a parte genérica foi extraída para um helper compartilhado novo: resolveSameContentFileIds (src/features/construction/evidenceReuse.service.js). Esse helper faz duas consultas:
  1. Busca todos os File cujos id estão em fileIds (os arquivos anexados ao RDO atual) e coleta o conjunto de checksumSha256 únicos.
  2. Busca TODOS os File da empresa (qualquer registro, qualquer obra) que compartilham qualquer um desses checksums — isso cobre tanto reuso do MESMO arquivo (mesmo id) quanto reupload do MESMO conteúdo com bytes idênticos mas id de arquivo diferente (o caso mais "suspeito": alguém baixou a foto, re-subiu com outro nome).
Em dailyReports.service.js, detectDailyReportEvidenceReuse (linha 24) chama esse helper e depois faz sua PRÓPRIA consulta específica de domínio: busca em DailyReport.evidenceFileIds (usando Op.overlap no Postgres array) por qualquer outro RDO da mesma empresa que já usou algum desses file-ids "mesmo conteúdo". Se encontrar, pega o mais antigo (order: created_at ASC) como referência. O resultado é gravado em 3 colunas no próprio RDO: evidenceReuseFlagged (boolean), evidenceReuseReferenceId (aponta pro RDO original) e evidenceReuseDetails (JSON com os file-ids sobrepostos e timestamp). Importante: isso NUNCA bloqueia a criação do RDO — é só um sinalizador para revisão humana, mesmo padrão/filosofia de "NAY sugere, nunca decide" usado em todo o sistema.

// src/features/construction/evidenceReuse.service.js (linhas 18-30)
async function resolveSameContentFileIds(fileIds, companyId, transaction) {
  if (!Array.isArray(fileIds) || !fileIds.length) return [];

  const attachedFiles = await File.findAll({ where: { id: { [Op.in]: fileIds }, companyId }, transaction });
  const checksums = [...new Set(attachedFiles.map((f) => f.checksumSha256).filter(Boolean))];
  if (!checksums.length) return [];

  const sameContentFiles = await File.findAll({ where: { checksumSha256: { [Op.in]: checksums }, companyId }, transaction });
  return sameContentFiles.map((f) => f.id);
}

// src/features/construction/dailyReports.service.js (linhas 24-47)
async function detectDailyReportEvidenceReuse(fileIds, companyId, excludeDailyReportId, transaction) {
  if (!Array.isArray(fileIds) || !fileIds.length) return { flagged: false, referenceId: null, details: null };

  const sameContentFileIds = await resolveSameContentFileIds(fileIds, companyId, transaction);
  if (!sameContentFileIds.length) return { flagged: false, referenceId: null, details: null };

  const where = {
    companyId,
    evidenceFileIds: { [Op.overlap]: sameContentFileIds },
  };
  if (excludeDailyReportId) where.id = { [Op.ne]: excludeDailyReportId };

  const priorMatches = await DailyReport.findAll({ where, transaction, order: [['created_at', 'ASC']] });
  if (!priorMatches.length) return { flagged: false, referenceId: null, details: null };

  const reference = priorMatches[0];
  const overlappingFileIds = reference.evidenceFileIds.filter((id) => sameContentFileIds.includes(id));

  return {
    flagged: true,
    referenceId: reference.id,
    details: { overlappingFileIds, matchedAt: new Date().toISOString() },
  };
}

Geração automática de tarefas por ausência de diário ou de documentos

Resolvido

O que a Nayara pediu, em linguagem simples: Se uma obra ativa não teve diário registrado num dia útil, ou se um trabalhador aparece no diário sem a documentação anexada, o sistema precisa criar automaticamente uma tarefa de acompanhamento para alguém resolver — sem precisar de um humano lembrando de verificar isso manualmente.

Como funciona
Dois detectores independentes em src/engines/jobs/missingDailyReportJob.js, ambos reaproveitando a mesma infraestrutura (janela de dias úteis, lock por advisory lock do Postgres, dedupe por Task já aberta) para não duplicar mecanismo, só mudando O QUE é verificado:
  1. detectMissingDailyReports (linha 30): para cada Project com status = 'ACTIVE', verifica se existe um DailyReport com reportDate igual ao dia útil anterior (previousBusinessDay, que pula sábado/domingo). Se não existe, cria uma Task em core.tasks com relatedEntityType = 'construction.projects', atribuída ao responsibleUserId do projeto, prioridade HIGH.
  2. detectMissingWorkerDocuments (linha 95, GAP fechado nesta sessão): para cada obra ativa, olha os RDOs dos últimos 7 dias úteis (MISSING_WORKER_DOCUMENTS_WINDOW_DAYS) e busca DailyWorker com documentFileIds vazio ou nulo ([Op.or]: [{ documentFileIds: [] }, { documentFileIds: null }]). Se achar qualquer um, cria uma Task com relatedEntityType = 'construction.daily_workers' (tipo distinto, para não se confundir com a tarefa de "RDO ausente"), prioridade MEDIUM.
Idempotência (bug real corrigido nesta rodada): o dedupe original era "check-then-create" puro, sem lock — em deploy multi-réplica, duas réplicas podiam checar "não existe Task ainda" ao mesmo tempo, antes de qualquer INSERT comitar, e criar duas tarefas duplicadas pro mesmo projeto/dia. A correção usa pg_advisory_xact_lock(hashtext(:key)) com uma chave única por projeto+dia (job 1) ou projeto+janela (job 2) — o lock serializa o check-then-create e é liberado automaticamente no commit/rollback da transação. Além do lock, o dedupe final também verifica se já existe uma Task com o mesmo título + relatedEntityId e status != 'CANCELED'.

Variações da chave lógica por data, turno e idempotência

Resolvido

O que a Nayara pediu, em linguagem simples: O sistema precisa saber distinguir "o mesmo diário sendo reenviado por engano" (ex.: app de campo sem internet reenviando quando a conexão volta) de "dois diários legítimos e diferentes no mesmo dia" (ex.: turno da manhã e turno da tarde) — sem duplicar o primeiro caso nem bloquear o segundo.

Como funciona
Existem DUAS camadas de identidade para um RDO, cada uma resolvendo um problema diferente:
  1. Chave lógica de negócio — (project_id, report_date, shift_code): define o que É um "mesmo diário" do ponto de vista de domínio. shiftCode é normalizado para maiúsculas via normalizeShiftCode (linha 51-53), com default 'UNICO' quando a obra só roda um turno — isso evita que 'manha' e 'MANHA' sejam tratados como turnos diferentes por acidente de digitação/capitalização no app de campo. Essa chave é checada ANTES da criação (DailyReport.findOne com os 3 campos) e lança DAILY_REPORT_DUPLICATE em caso de colisão — isto impede duplicação acidental de um diário pelo MESMO turno, mas permite >1 RDO por dia em turnos diferentes (ex.: MANHA + TARDE + NOITE na mesma obra, mesma data).
  2. Idempotência de captura offline — idempotencyKey: resolve um problema DIFERENTE — o app de campo gerou o RDO offline, tentou sincronizar, a sincronização pode ter "dado certo no servidor mas a resposta se perdeu na rede" (timeout do lado do cliente), e o app reenvia o MESMO payload ao reconectar. Checada ANTES até da checagem de chave lógica (linha 162-167): se idempotencyKey já existe no banco, devolve o registro JÁ CRIADO (sem erro, sem duplicar) — diferente da chave lógica, que lança erro de conflito. Essa é a diferença de design importante: duplicar via chave lógica é um ERRO do usuário (tentando criar dois diários "iguais" de propósito); duplicar via idempotencyKey é uma RETENTATIVA técnica do mesmo app, então o comportamento correto é devolver sucesso silencioso com o registro original.
O UNIQUE parcial do banco (mencionado no código como garantia final) existe como última linha de defesa contra condição de corrida entre o findOne de checagem e o create — mesmo padrão de "checagem otimista + constraint de banco como rede de segurança" usado em outras partes do sistema (ex.: pg_advisory_xact_lock no job de RDO ausente).

Resolvido

O que a Nayara pediu, em linguagem simples: uma medição de obra não pode passar direto de "rascunho" para "aprovada" — precisa existir um rastro claro de quem lançou, quem revisou tecnicamente e quem aprovou financeiramente, nessa ordem, sem pular etapas. Isso evita que uma medição errada vire pagamento sem ninguém conferir antes.

Como funciona
A medição (StageMeasurement) é uma máquina de estados com 7 status possíveis: DRAFT, SUBMITTED, REVIEWED, APPROVED, PAYABLE, REJECTED, SUPERSEDED. Cada transição é uma função própria em stageMeasurements.service.js:
  • createStageMeasurement — nasce em DRAFT, com itens (quantidade × preço unitário) que somam o totalAmount em centavos inteiros (evita erro de ponto flutuante).
  • submitStageMeasurement — DRAFT → SUBMITTED, dispara o evento de domínio measurement.submitted.
  • reviewStageMeasurement — SUBMITTED → REVIEWED, etapa técnica sem nenhum efeito financeiro (só registra quem revisou e observações).
  • decideStageMeasurement — REVIEWED → APPROVED → PAYABLE, tudo na MESMA transação: grava measuredPct na etapa da obra, cria a obrigação financeira real (createPayableForMeasurement) e só então avança para PAYABLE. Uma medição nunca fica "aprovada sem lançamento financeiro" — se o lançamento falhar, a transação inteira é revertida (nenhuma medição fica presa em APPROVED sem PAYABLE).
A função assertTransition é o guarda de trânsito: recebe a lista de estados de origem permitidos e lança STAGE_MEASUREMENT_INVALID_STATUS com mensagem em português (rótulos amigáveis, não o enum cru) se a medição não estiver no estado certo.

Idempotência por source_event_id, sem duplicação de contas a pagar

Resolvido

O que a Nayara pediu, em linguagem simples: se o mesmo evento de aprovação for reprocessado por engano (duplo clique, reenvio de fila, retry de rede), o sistema não pode criar duas contas a pagar para a mesma medição — tem que reconhecer que já processou aquilo e devolver o resultado já existente.

Como funciona
A idempotência é construída em DUAS camadas de defesa, propositalmente redundantes:
  1. 1ª camada — lock pessimista: getStageMeasurement(id, transaction, { lock: true }) usa SELECT ... FOR UPDATE antes de checar o status. Duas aprovações concorrentes da mesma medição serializam no lock — a segunda só enxerga a medição já fora de [SUBMITTED, REVIEWED] (porque a primeira já commitou) e falha com STAGE_MEASUREMENT_INVALID_STATUS antes mesmo de tentar criar o lançamento.
  2. 2ª camada — UNIQUE no banco (cinto e suspensório): mesmo que algo rompa o lock (bug futuro, dado corrompido), a chave de idempotência do Financeiro é determinística — measurement.payable:<measurementId> — e é UNIQUE em finance.financial_entries.idempotency_key. O segundo INSERT colidiria com a constraint; createFinancialEntry intercepta isso via assertNoDuplicatePayment e devolve um erro de negócio limpo (FINANCE_DUPLICATE_PAYMENT) em vez de estourar como erro de constraint cru no banco.

Reaproveitamento de materiais

Resolvido

O que a Nayara pediu, em linguagem simples: material que sobrou ou voltou em bom estado de uma obra precisa poder ser reaproveitado — voltar para o estoque normal, disponível para outra requisição, em vez de ficar "perdido" dentro da obra que já encerrou aquela etapa.

Como funciona
O reaproveitamento é o caminho conditionCode: 'REUSABLE' (default) de returnMaterialRequest: o movimento RETURN credita o saldo de volta no item/local normal do Estoque — o mesmo saldo (inventory.stock_balances) de onde qualquer outra requisição de material de qualquer obra consome via recordMovement tipo OUT. Não existe uma "fila separada de material reaproveitado": ele entra de volta no ledger físico único do item, imediatamente disponível para a próxima requisição que pedir aquele mesmo inventoryItemId/sourceLocationId. A idempotência por requisição (material_request.return:<id>) garante que reenviar a mesma devolução não credita o saldo duas vezes — importante justamente para não "reaproveitar" o mesmo material fisicamente duas vezes na contagem.

Há também um segundo mecanismo de reaproveitamento, específico de perdas de material em obra (lossRecords.service.js): returnLossRecord permite devolver (parcial ou totalmente) uma perda já aprovada, criando um registro RETURN que aponta para o LOSS original via relatedLossRecordId — o saldo agregado (getMaterialBalance) soma LOSS (negativo) + RETURN (positivo), corrigindo a quantidade/valor disponível sem nunca apagar o registro histórico original da perda (append-only).

Motivo obrigatório, alçada e aprovação conforme o valor (Obras e Estoque)

Resolvido

O que a Nayara pediu, em linguagem simples: toda perda precisa ter um motivo escrito — não pode ser registrada "sem explicação" — e, se o valor da perda for alto, isso não pode ser decidido automaticamente: tem que passar por alguém com permissão de aprovar. Se for um valor pequeno, o sistema pode liberar sozinho para não travar a operação no dia a dia.

Como funciona
Existem dois mecanismos de alçada por valor, paralelos e intencionalmente independentes, compartilhando a MESMA tabela genérica construction.approval_thresholds (chave companyId + context, UNIQUE):
  1. Obras — LossRecord (contexto MATERIAL_LOSS): em createLossRecord, o reason é obrigatório desde a validação de entrada (não cria sem). O valor (estimatedValue) é comparado contra getApprovalThreshold — se não houver linha configurada para a empresa, usa o fallback de fábrica DEFAULT_MAX_AUTO_APPROVE_AMOUNT = 1000.0. Dentro do limite → nasce APPROVED direto; acima → PENDING_APPROVAL, exigindo approveLossRecord explícito (que só aceita partir de PENDING_APPROVAL, fail-closed).
  2. Estoque — InventoryLossCase (contexto INVENTORY_LOSS): em openLossCase, context (o motivo) é obrigatório desde a validação de entrada, assim como pelo menos uma evidência (evidenceFileIds, EST-TS-10). Diferente de Obras, aqui NÃO existe fallback numérico de fábrica — a alçada só é avaliada quando a empresa já configurou explicitamente uma linha para INVENTORY_LOSS via upsertApprovalThreshold (decisão de engenharia documentada: preserva 100% o comportamento anterior — sempre exigir decisão humana via inventory:approve — para quem não configurou nada). Quando configurado e o estimatedCost está dentro do limite, o próprio openLossCase chama internamente decideLossCase com um ator sintético canApprove: true representando a regra de negócio decidindo (não um usuário burlando permissão).
Em ambos os casos, upsertApprovalThreshold valida Number.isFinite e um teto de sanidade (1_000_000_000_000) — um bug real já corrigido impedia que Infinity/"NaN" fossem salvos como limite (o que faria TUDO autoaprovar).

Resolvido

Resolvido

Resolvido

O que a Nayara pediu, em linguagem simples: não dá para fechar um chamado de garantia só dizendo "resolvido" — precisa constar o motivo real do problema (causa raiz), uma foto de antes e de depois do reparo, e ao menos um registro de que alguém realmente foi lá e fez algo.

Escalonamento automático por vencimento de SLA

Resolvido

O que a Nayara pediu, em linguagem simples: se um chamado de garantia estiver perto do prazo (ou já vencido) e ninguém atendeu, o sistema precisa avisar sozinho — não pode depender de alguém abrir o painel manualmente para descobrir que um prazo estourou.

Como funciona
Um job periódico (warrantyEscalationJob, a cada 30 minutos por padrão) varre todos os MaintenanceCase ainda não CLOSED com slaDueAt definido, e recalcula o nível de escalonamento usando a MESMA função pura (computeEscalationLevel) que o service usa ao criar/editar um caso manualmente — garantindo que o nível mostrado nunca diverge entre "editei agora" e "o job rodou por cima". A regra: já vencido → OVERDUE; vence em até 1 dia → CRITICAL; até 2 dias → WARNING; mais que isso → NONE. Só CRITICAL e OVERDUE disparam notificação real (Notification no banco + evento warranty.case.escalated na Outbox) para o responsibleUserId do caso — WARNING é só um aviso prévio silencioso. O job é idempotente (só grava/notifica quando o nível calculado realmente muda) e cada caso é processado numa transação aninhada própria com lock pessimista e savepoint — um caso com problema (ex.: responsável órfão) não aborta o escalonamento dos outros casos da mesma empresa no mesmo ciclo.
Código real
// src/engines/jobs/warrantyEscalationJob.js
function computeEscalationLevel(slaDueAt, now = new Date()) {
  if (!slaDueAt) return 'NONE';
  const diffMs = new Date(slaDueAt).getTime() - new Date(now).getTime();
  if (diffMs < 0) return 'OVERDUE';
  const diffDays = diffMs / DAY_MS;
  if (diffDays <= 1) return 'CRITICAL';
  if (diffDays <= 2) return 'WARNING';
  return 'NONE';
}

for (const warrantyCase of candidates) {
  const newLevel = computeEscalationLevel(warrantyCase.slaDueAt, now);
  if (newLevel === warrantyCase.escalationLevel) continue;
  await sequelize.transaction({ transaction }, async (nested) => {
    const locked = await MaintenanceCase.findByPk(warrantyCase.id, { transaction: nested, lock: nested.LOCK.UPDATE });
    const confirmedLevel = computeEscalationLevel(locked.slaDueAt, now);
    if (confirmedLevel === locked.escalationLevel) return;
    locked.escalationLevel = confirmedLevel;
    await locked.save({ transaction: nested });
    if (NOTIFIABLE_LEVELS.includes(confirmedLevel)) {
      await publishWarrantyCaseEscalated(locked, nested);
      if (locked.responsibleUserId) {
        await Notification.create({ ..., title: confirmedLevel === 'OVERDUE' ? 'Chamado de garantia vencido' : 'Chamado de garantia crítico', ... }, { transaction: nested });
      }
    }
  });
}

Desconto ou ressarcimento com alçada, aprovação e integração financeira

Resolvido

O que a Nayara pediu, em linguagem simples: quando a empresa decide dar um desconto ou devolver dinheiro ao cliente por causa de um problema de garantia, isso não pode ser um "combinado de boca" — precisa ter regra de valor (abaixo de um limite, aprova sozinho; acima, precisa de aprovação explícita de alguém) e isso precisa gerar um lançamento real no Financeiro, não ficar só anotado no chamado.

Como funciona
proposeWarrantyResolution recebe resolutionType (DISCOUNT ou REIMBURSEMENT) e resolutionAmount (precisa ser número finito > 0). Compara o valor contra uma alçada configurável por empresa (getApprovalThreshold, contexto WARRANTY_RESOLUTION, mesmo mecanismo de alçada já usado para perda de material em obra — lossRecords.service.js, default de fábrica R$ 1.000,00). Dentro da alçada: o registro já nasce resolutionStatus='APPROVED', com resolutionApprovedByUserId preenchido automaticamente, e CRIA IMEDIATAMENTE um lançamento financeiro real via financialEntriesService.createFinancialEntry — nenhum financeiro paralelo ou fake, é o mesmo service usado pelo resto do sistema. Acima da alçada: nasce PENDING_APPROVAL, sem nenhum lançamento financeiro ainda, e exige uma chamada explícita e separada a approveWarrantyResolution antes de gerar qualquer efeito financeiro. O lançamento é criado com idempotencyKey: warranty.resolution:{id do caso} — aprovar a MESMA resolução mais de uma vez nunca duplica o lançamento. O centro de custo usado (OBRAS-GARANTIA) é resolvido/criado automaticamente na primeira vez (lazy, uma vez por empresa), porque o Financeiro exige centro de custo obrigatório em toda despesa e este fluxo automático não tem como pedir esse dado a um humano no momento da aprovação.

// maintenanceCases.service.js
async function proposeWarrantyResolution(id, payload, actorUserId, transaction) {
  const maintenanceCase = await getMaintenanceCase(id, transaction, true);
  // ...valida resolutionType e resolutionAmount...
  const threshold = await getApprovalThreshold(maintenanceCase.groupId, maintenanceCase.companyId, CONTEXT_WARRANTY_RESOLUTION, transaction);
  const withinThreshold = numericAmount <= threshold;
  maintenanceCase.resolutionStatus = withinThreshold ? 'APPROVED' : 'PENDING_APPROVAL';
  if (withinThreshold) {
    maintenanceCase.resolutionApprovedByUserId = actorUserId || null;
    await createWarrantyResolutionFinancialEntry(maintenanceCase, actorUserId, transaction);
  }
  await maintenanceCase.save({ transaction });
  return maintenanceCase;
}

  const costCenter = await getOrCreateDefaultCostCenter(maintenanceCase.groupId, maintenanceCase.companyId, 'OBRAS-GARANTIA', 'Pós-obra — garantia', transaction);

  }, actorUserId, transaction);
  maintenanceCase.resolutionFinancialEntryId = entry.id;
  return entry;
}

1.8.1 Resumo de andamento, comparação de cronograma e projeção de custos

Resolvido

O que a Nayara pediu, em linguagem simples: Que exista um componente nomeado "NAY Obras" que, ao ser consultado, devolva um resumo de como a obra está indo: quanto já foi executado fisicamente versus o que deveria ter sido executado até hoje (cronograma), quanto já foi gasto, quanto ainda falta gastar e se a margem financeira projetada está saudável ou não. Como funciona

1.8.2 Detecção de ausência de diário ou documentos

Resolvido

O que a Nayara pediu, em linguagem simples: Que o sistema perceba sozinho quando o diário de obra (RDO) não está sendo preenchido nos dias em que deveria, e quando um trabalhador aparece no diário sem nenhum documento anexado (ex.: identidade, ASO). Isso evita que a ausência de registro só seja descoberta quando já é tarde demais (ex.: numa fiscalização ou acidente).

Como funciona
Duas contagens entram no resumo de summarizeProject: missingDailyReportDays e workersWithoutDocuments.

countMissingDailyReportDays usa o mesmo helper de dias úteis já usado pelo job de produção missingDailyReportJob.js (lastBusinessDays, em src/engines/jobs/businessDays.helper.js) para pegar os últimos 10 dias úteis (MISSING_DAILY_REPORT_WINDOW_BUSINESS_DAYS = 10), busca todos os DailyReport da obra nesse intervalo e conta quantos desses dias úteis NÃO têm nenhum RDO registrado. Não duplica a regra de "o que é dia útil" — reusa a mesma fonte do job que já roda em produção, para as duas camadas nunca divergirem.

countWorkersWithoutDocuments busca todos os DailyReport da obra, depois todos os DailyWorker vinculados a esses relatórios, e conta quantos têm documentFileIds vazio ou ausente (!Array.isArray(w.documentFileIds) || w.documentFileIds.length === 0).

2.1 company_id, RLS e isolamento entre empresas

Resolvido

O que a Nayara pediu, em linguagem simples: Que seja impossível uma empresa (tenant) enxergar ou alterar dados de outra empresa dentro do mesmo banco de dados compartilhado — mesmo que alguém tente contornar a aplicação e mandar um comando SQL direto no banco.

Como funciona
Toda tabela multiempresa do módulo Obras tem Row-Level Security (RLS) do próprio PostgreSQL habilitado com ENABLE ROW LEVEL SECURITY + FORCE ROW LEVEL SECURITY (o FORCE é o que impede até o dono da tabela de contornar a política), mais uma política tenant_isolation do tipo deny-by-default que compara company_id da linha contra a variável de sessão app.company_id, setada pelo middleware de tenant a cada requisição (SET LOCAL app.company_id = ... dentro da própria transação). Isso significa que o isolamento acontece NO BANCO, não só em cláusulas WHERE escritas à mão na aplicação — mesmo uma query SQL manual que "esqueça" o filtro de empresa é bloqueada pelo Postgres antes de devolver ou alterar qualquer linha. Além disso, desde 18/09/2026 o próprio CI foi corrigido para rodar a suíte de testes com um usuário de banco SEM BYPASSRLS/SUPERUSER (nayara_ci_app), exatamente igual ao usuário de produção (nayara_runtime) — antes disso, o CI rodava com o usuário inicial do container Postgres oficial, que é superuser por padrão e ignora RLS silenciosamente, mascarando qualquer regressão de isolamento.

2.3 Locks, permissões, congelamento de baseline, transações de aprovação + Controle de concorrência por lock_version

Resolvido

O que a Nayara pediu, em linguagem simples: Que, quando duas pessoas tentam aprovar ou alterar a mesma medição/orçamento ao mesmo tempo (ex.: dois cliques, duas abas abertas, duas requisições simultâneas), o sistema não deixe acontecer uma "corrida" onde a segunda ação sobrescreve a primeira silenciosamente ou cria dois efeitos financeiros para a mesma coisa. E que, uma vez que um orçamento é aprovado (vira "baseline"), ele fique congelado — não dá mais para editar silenciosamente um valor que já foi usado para calcular margem/comissão.

Como funciona
Dois mecanismos de controle de concorrência trabalham juntos: lock otimista (coluna lock_version, incrementada pelo Sequelize a cada .save() via version: 'lockVersion' no model) e lock pessimista (SELECT ... FOR UPDATE real do Postgres, via transaction.LOCK.UPDATE do Sequelize) nas operações que decidem o estado de uma medição. A função getStageMeasurement(id, transaction, { lock }) em stageMeasurements.service.js trava a linha com FOR UPDATE sempre que a chamada vai TRANSICIONAR o estado (submeter, revisar, revisar/corrigir, decidir) — isso significa que, se duas requisições concorrentes tentam decidir a mesma medição, a segunda só consegue ler a linha DEPOIS que a primeira transação commitou, então ela enxerga o novo status (ex.: já PAYABLE) e falha com STAGE_MEASUREMENT_INVALID_STATUS em vez de aplicar uma segunda decisão silenciosa. 2.4 Criação transacional de diário e publicação de eventos na Outbox + Aprovação de medições com lock e Outbox

Resolvido

O que a Nayara pediu, em linguagem simples: Que, quando um diário de obra é criado ou uma medição é aprovada, o evento que avisa o resto do sistema (outros módulos, BI, integrações futuras) seja gravado na MESMA transação do banco que grava o dado em si — nunca separado, para nunca existir um estado onde "o dado foi salvo mas ninguém soube" ou "o evento foi disparado mas o dado não foi salvo de verdade".

Como funciona
O projeto usa o padrão Transactional Outbox: toda publicação de evento de domínio grava uma linha em integration.outbox_events DENTRO da mesma transação Sequelize da operação de negócio que o originou — nunca depois, nunca "direto no broker" fora da transação. A função central é publishDomainEvent(event, transaction) em src/engines/events/outbox.js, chamada por todos os publishers do módulo Obras (src/features/construction/constructionEvents.service.js). Para o diário de obra, publishDailyLogCreated(report, transaction) publica project.daily_log.created na mesma transação de dailyReportsService.createDailyReport. Para medições, publishMeasurementSubmitted/publishMeasurementApproved publicam measurement.submitted/measurement.approved dentro da MESMA transação de decideStageMeasurement — que também cria a obrigação financeira (createPayableForMeasurement) e avança o status para PAYABLE, tudo atômico: se qualquer parte falhar, a transação inteira é revertida (dado, evento e lançamento financeiro nascem ou morrem juntos).

2.5 Idempotência de eventos e prevenção de duplicidade financeira

Resolvido

O que a Nayara pediu, em linguagem simples: Que reprocessar o mesmo evento duas vezes (reenvio de mensagem, duplo clique, retry de rede) nunca gere duas contas a pagar para a mesma medição aprovada, nem dois eventos duplicados no barramento de integração.

Como funciona
Toda linha de integration.outbox_events tem uma coluna idempotency_key com constraint UNIQUE no banco — publishDomainEvent recusa (erro OUTBOX_IDEMPOTENCY_KEY_MISSING) publicar qualquer evento sem essa chave. As chaves são derivadas deterministicamente do id do agregado (ex.: measurement.approved:<measurementId> — fixa por medição, nunca por tentativa), então reprocessar o mesmo evento colide no índice único e falha, em vez de duplicar silenciosamente. Para o caso financeiro mais crítico (aprovação de medição gerando conta a pagar), a prevenção de duplicidade tem DUAS camadas, documentadas explicitamente no código: (1) lock pessimista em getStageMeasurement(..., { lock: true }) — a segunda chamada concorrente só enxerga a medição já fora de [SUBMITTED, REVIEWED] e falha antes de tentar criar o lançamento; (2) mesmo que a primeira defesa falhe por algum bug futuro, a idempotency_key UNIQUE de finance.financial_entries (measurement.payable:<measurementId>) faz o segundo INSERT falhar no banco, e assertNoDuplicatePayment intercepta isso com um erro de negócio claro (FINANCE_DUPLICATE_PAYMENT) em vez de um erro de constraint cru.

2.6 Logs correlacionados dos eventos mínimos do módulo

Resolvido

O que a Nayara pediu, em linguagem simples: Que seja possível, dado um problema relatado por um usuário, reconstruir TODA a cadeia de ações que uma única requisição HTTP disparou (auditoria + eventos de domínio), sem precisar adivinhar qual log pertence a qual requisição.

Como funciona
Implementado via correlationId propagado com AsyncLocalStorage nativo do Node (src/middlewares/correlationId.middleware.js) — identificado internamente como TEC-08. A cada requisição HTTP, o middleware aceita um X-Correlation-Id vindo do cliente (rastreamento ponta a ponta real, front → API) ou gera um novo UUID, e guarda esse valor num contexto assíncrono que sobrevive por toda a cadeia de chamadas da requisição — sem precisar que cada um dos ~150 pontos do código que chamam registrarAuditoria/publishDomainEvent passe o parâmetro manualmente (decisão de engenharia documentada: alterar todos esses pontos seria um risco de regressão alto demais sob prazo). Tanto audit.audit_log.correlation_id quanto integration.outbox_events.correlation_id são colunas UUID reais (não texto livre) — publishDomainEvent preenche automaticamente via getCurrentCorrelationId() quando o chamador não informa explicitamente.
Código real
const correlationIdStorage = new AsyncLocalStorage();
const UUID_PATTERN = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

function correlationIdMiddleware(req, res, next) {
  const incoming = req.headers['x-correlation-id'];
  const correlationId = (typeof incoming === 'string' && UUID_PATTERN.test(incoming.trim()))
    ? incoming.trim()
    : crypto.randomUUID();
  req.correlationId = correlationId;
  res.setHeader('X-Correlation-Id', correlationId);
  correlationIdStorage.run({ correlationId }, () => next());
}

function getCurrentCorrelationId() {
  return correlationIdStorage.getStore()?.correlationId || null;
}

2.9 Restore reproduzível

Resolvido

O que a Nayara pediu, em linguagem simples: Que exista uma forma real e testada de fazer backup do banco e, se precisar, restaurar esse backup num banco novo — com prova de que depois do restore os dados batem exatamente com o original (mesmo número de tabelas, mesmo número de linhas).

Como funciona
Dois scripts Node reais, scripts/backupDatabase.js e scripts/restoreDatabase.js, usando as ferramentas nativas do Postgres (pg_dump/pg_restore via shell), nunca uma reimplementação própria de dump. O backup lê DATABASE_URL (ou as variáveis DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD) do ambiente e gera um dump em formato custom (pg_dump -Fc, que permite restore seletivo e é comprimido) em backups/<nome-do-banco>_<timestamp>.dump (pasta ignorada pelo git, para nunca commitar dados de produção). O restore exige um --target-db explícito e recusa rodar se esse valor for igual ao banco principal do ambiente — proteção ativa contra sobrescrever produção/dev por engano ao testar um restore.
Código real
Comandos reais de uso, documentados em scripts/README-backup-restore.md: 
node scripts/backupDatabase.js [--out ]

node scripts/restoreDatabase.js --file  --target-db
